LawCompass 발표 대비 기술 딥다이브

RAG, Agent, Gateway, Worker까지 한 번에 설명하는 전체 구조 자료

이 문서는 발표자가 “왜 이런 구조를 선택했는지”까지 답할 수 있도록, 실제 프로젝트의 서비스 구성, RAG 동작 방식, 영상 분석 흐름, 과실비율 산정 흐름, 대체 기술과의 비교를 한 HTML 페이지에 정리한 자료입니다.

Frontend Vue 3 + Vite
Gateway Fastify + Redis Job
Agent FastAPI + RAG Pipeline
Storage PostgreSQL + pgvector

1. 발표에서 먼저 말할 핵심 요약

처음 30초 안에 프로젝트 구조를 설명할 때 쓰기 좋은 요약입니다.

한 문장 요약

LawCompass는 사고 설명과 영상을 입력받아 사고 대분류를 먼저 고정하고, 그 대분류 안에서만 KNIA 과실비율 인정기준과 법률 근거를 RAG로 검색한 뒤, Agent가 구조화된 판단 계약에 맞춰 사용자에게 이해 가능한 결과를 만드는 교통사고 분석 서비스입니다.

대분류 우선 KNIA 구조화 JSON pgvector RAG 영상 관찰값 보조 LLM 숫자 생성 제한
발표 포인트: “AI가 마음대로 과실비율을 찍는 서비스”가 아니라, 구조화된 KNIA 기준과 RAG 근거를 우선하고, AI는 분류·요약·질문·설명 보조에 쓰는 구조라고 설명하면 됩니다.

2. 전체 MSA 구성

웹 요청, 장기 영상 분석, AI 판단, DB/RAG를 분리해 장애 범위와 책임을 나눴습니다.

Frontend

Vue 3 화면. 사고 설명, 영상 업로드, 질문 답변, 결과 확인을 담당합니다.

Gateway

Fastify API. 인증된 케이스 요청을 받고 DB 저장, Agent 호출, Worker Job 생성을 담당합니다.

Redis Stream

영상 전처리와 장기 분석 Job을 큐로 분리합니다. 사용자는 API 응답을 오래 기다리지 않습니다.

Worker

ffprobe/ffmpeg로 영상 메타와 프레임을 만들고 YOLO/OpenAI 관찰값을 생성합니다.

Agent

FastAPI 분석 엔진. 대분류 라우팅, KNIA/RAG 검색, 과실 분석, 결과 계약 생성을 담당합니다.

PostgreSQL

케이스, Job, 결과, KNIA 구조화 기준, RAG chunk, pgvector embedding을 저장합니다.

왜 분리했나?

  • 영상 분석은 오래 걸립니다. 업로드 요청에서 바로 처리하면 timeout과 사용자 이탈이 커집니다.
  • AI 판단은 Python 생태계가 유리합니다. FastAPI Agent에서 RAG, 임베딩, 영상 관찰값, 분석 파이프라인을 다룹니다.
  • Gateway는 제품 API의 안정성을 담당합니다. 사용자 요청, 케이스 저장, Job 상태, 결과 조회를 TypeScript로 명확히 관리합니다.
  • DB와 RAG를 한 저장소에 둡니다. PostgreSQL과 pgvector로 운영 복잡도를 줄이고 트랜잭션 데이터와 벡터 검색을 함께 다룹니다.

발표용 설명

“저희는 모든 것을 하나의 서버에서 처리하지 않았습니다. 사용자가 바로 응답을 받아야 하는 요청은 Gateway가 처리하고, 오래 걸리는 영상 분석은 Worker로 넘깁니다. Agent는 판단과 근거 검색에 집중하도록 분리했습니다. 이 구조 덕분에 영상 분석 실패가 전체 API 장애로 번지지 않고, 분석 모델과 웹 API를 독립적으로 개선할 수 있습니다.”

3. 요청 흐름

자연어 분석과 영상 분석은 진입점은 다르지만 결국 Agent의 공통 분석 파이프라인으로 모입니다.

자연어 분석

  1. Frontend가 사고 설명과 선택 답변을 Gateway에 보냅니다.
  2. Gateway가 케이스 권한과 입력을 검증하고 초기 사실을 병합합니다.
  3. Gateway가 Agent의 /internal/v1/analyze/text를 호출합니다.
  4. Agent가 대분류, 시나리오, KNIA 기준, 법률 근거, 질문을 생성합니다.
  5. Gateway가 결과를 DB에 저장하고 사용자용 report/easy-report로 반환합니다.

영상 분석

  1. Frontend가 영상을 업로드하고 분석을 요청합니다.
  2. Gateway가 video_analyze 또는 전처리 Job을 Redis Stream에 넣습니다.
  3. Worker가 영상을 로컬에서 materialize하고 ffprobe/ffmpeg로 프레임을 추출합니다.
  4. YOLO와 OpenAI 프레임 분석으로 차량, 보행자, 충돌 후보를 관찰값으로 만듭니다.
  5. Worker가 관찰값을 Agent의 /internal/v1/analyze/video로 보내 결과를 저장합니다.

추가 질문 후 재분석

  1. 결과에서 부족한 사실을 질문으로 받습니다.
  2. 사용자 답변은 structured_facts로 저장됩니다.
  3. Gateway의 reanalyze가 기존 결과와 새 답변을 합칩니다.
  4. Agent는 같은 대분류 안에서 KNIA 기준과 가감요소를 다시 평가합니다.
  5. 결과는 확정값, 범위, 조건별 결과로 업데이트됩니다.

4. RAG를 위해 한 작업

핵심은 “문서를 그냥 벡터로 넣는 것”이 아니라, KNIA 기준을 구조화 chart와 설명 chunk로 나눠 연결한 점입니다.

RAG 데이터 모델

KNIA 2023.6 자동차사고 과실비율 인정기준 JSON은 크게 charts와 rag_documents로 나뉩니다. charts는 과실비율 산정에 쓰는 구조화 기준이고, rag_documents는 사용자에게 근거를 설명하기 위한 RAG chunk입니다.

charts

  • chart_no: 차41, 차43, 보 계열 등 기준 번호
  • major_party_type: car_vs_car, car_vs_person 등 대분류
  • scenario_type: rear_end_collision, lane_change_collision 등 세부 사고유형
  • base_fault: A/B 기본 과실 후보
  • adjustments: 수정요소, 가감요소
  • review_required: 검수 필요 여부

rag_documents

  • doc_id: chunk 식별자
  • chart_no: 어떤 기준에 연결되는지
  • major_party_type: 대분류 필터링용 metadata
  • scenario_type: 세부 사고유형 metadata
  • chunk_type: 기준 설명, 법규, 활용 참고사항 등
  • body: 임베딩과 근거 표시 대상 본문
중요한 설계: 과실비율 숫자는 RAG 본문에서 LLM이 새로 만들지 않습니다. 구조화 chart의 base_fault와 adjustments가 source of truth 후보이고, RAG chunk는 그 기준을 설명하고 법규를 보강하는 용도입니다.

Import 파이프라인

  1. knia_json_loader.py가 JSON의 metadata, pages, charts, rag_documents를 읽습니다.
  2. 필수 필드가 없으면 import를 중단하지 않고 validation warning으로 기록합니다.
  3. knia_json_repository.py가 charts를 knia_fault_charts에 upsert합니다.
  4. rag_documents는 reference document/chunk 구조로 저장하고 metadata에 chart_no, party, scenario를 보존합니다.
  5. knia_json_vectorizer.py가 chunk 본문을 embedding으로 변환해 pgvector 컬럼에 저장합니다.
python apps/agent/scripts/import_knia_fault_ratio_json.py \
  --path scripts/knia_fault_ratio/knia_fault_ratio_2023_06.codex_review.json \
  --rebuild-embeddings

검색 파이프라인

  1. Agent가 사고 대분류를 먼저 확정합니다.
  2. party_guard.py가 대분류에 맞지 않는 검색어와 chart prefix를 제거합니다.
  3. knia_matcher.py가 구조화 chart를 먼저 검색합니다.
  4. 선택된 chart_no가 있으면 RAG 검색을 해당 chart_no chunk로 제한합니다.
  5. chart_no가 없으면 같은 major_party_type 안에서만 fallback 검색합니다.
  6. 법률 RAG는 별도로 검색하되, 사고 축과 무관한 근거는 primary evidence에서 제외합니다.

5. RAG 검색 세부 동작

LawCompass의 RAG는 “정확한 대분류 안에서 구조화 기준을 찾고, 그 기준의 설명만 가져오는” 방식입니다.

RAG가 동작하는 순서

1. 입력 정규화

자연어, 영상 관찰값, 선택 답변을 facts로 정리합니다.

2. Party Guard

car_vs_person이면 보 계열, car_vs_car이면 차 계열만 허용합니다.

3. Structured Chart

chart_no, scenario_type, base_fault를 가진 구조화 기준을 먼저 찾습니다.

4. RAG Chunk

선택 chart_no 또는 같은 party 안의 chunk만 pgvector/keyword로 검색합니다.

5. Evidence Routing

근거를 primary, secondary, excluded로 나눠 결과에 반영합니다.

Two-stage cache를 둔 이유

search_knia_json_cached는 Redis exact cache, semantic query cache, pgvector 검색, keyword fallback을 함께 사용합니다. 같은 질문을 반복할 때는 Redis로 빠르게 응답하고, 비슷한 질문은 semantic query cache로 재사용하며, 임베딩이 실패해도 keyword fallback으로 최소 근거를 찾습니다.

Exact Redis Cache

완전히 같은 query/party/scenario/chart_no 요청은 바로 응답합니다.

Semantic Query Cache

비슷한 임베딩 쿼리는 이전 결과를 재활용합니다.

pgvector Search

chunk embedding과 질의 embedding의 벡터 거리를 기준으로 검색합니다.

Keyword Fallback

임베딩 provider가 없어도 chart_no, title, body keyword로 검색합니다.

대분류 누수 방지

과거 문제는 차대차 사고에서 보행자/자전거 기준이 섞이거나, 차대사람 사고에서 차대차 교차로 기준이 보이는 것이었습니다. 이를 막기 위해 party_guard.py가 chart prefix와 metadata를 모두 검사합니다.

차대사람

car_vs_person이면 KNIA chart prefix 보 계열만 최종 결과에 표시합니다.

차대차

car_vs_car이면 차41, 차43 같은 차 계열만 표시하고 보/거 기준은 제외합니다.

차대자전거

car_vs_bicycle이면 거 계열을 우선하고 후미추돌 차대차 기준은 표시하지 않습니다.

6. Agent 내부 동작 방식

Agent는 완전 자율형 에이전트가 아니라, 사고 분석에 맞춘 통제형 파이프라인입니다.

분석 파이프라인

  1. Input Normalizer: 자연어, 영상 관찰값, 프론트 선택값을 UTF-8 안전 문자열과 structured_facts로 정리합니다.
  2. Party Agent Router: 직접 충돌 대상을 먼저 찾아 car_vs_car, car_vs_person, car_vs_bicycle, car_vs_motorcycle, car_vs_object, single_vehicle 중 하나로 고정합니다.
  3. Scenario Classifier: 대분류를 흔들지 않고 그 안에서 후미추돌, 차선변경, 교차로, 보행자 작업자 사고 같은 세부 시나리오를 고릅니다.
  4. Evidence Stage: KNIA 구조화 chart, KNIA RAG chunk, 법률 RAG, static fallback 근거를 모으고 사고 축에 맞게 필터링합니다.
  5. Fault Ratio Analyst: KNIA base_fault와 가감요소 registry를 바탕으로 base_fault, final_fault, range, conditional_outcomes를 만듭니다.
  6. Judgment Contract: 충분한 근거가 있는지, 확정 가능한지, 추가 질문이 필요한지 판단 상태를 계약 형태로 정리합니다.
  7. Report Composer: 내부 trace와 raw metadata를 숨기고 사용자가 읽을 수 있는 결론, 근거, 질문, 대응 문장으로 변환합니다.
발표 포인트: “LLM이 자유롭게 판단하게 두는 대신, 직접 충돌 대상 → 대분류 → 시나리오 → KNIA chart → RAG 근거 → 가감요소 순서로 움직이는 통제형 Agent입니다. 그래서 잘못된 대분류 근거가 섞이는 위험을 줄였습니다.”

7. 예시로 보는 실제 판단

발표 중 질문을 받았을 때 설명하기 쉬운 대표 입력 예시입니다.

  • 시나리오: rear_end_collision

  • 브레이크등은 모름이므로 확정 반영하지 않고 조건별 결과로 둡니다.

예시 B. 공사 담당자 사고

입력

공사 담당자가 도로 폭 측정을 위하여

  • 시나리오: lane_change_collision

  • 방향지시등, 선진입, 충돌 부위는 가감요소 질문으로 이어집니다.

8. Gateway 자세한 역할

Gateway는 외부 API의 계약과 제품 데이터 흐름을 지키는 계층입니다.

주요 책임

  • 케이스 생성, 목록, 상세, 수정 API를 제공합니다.
  • 영상 업로드 초기화, 완료 처리, 케이스별 업로드 조회를 담당합니다.
  • 자연어 분석 요청을 Agent 내부 API로 전달하고 결과를 DB에 저장합니다.
  • 영상 분석은 Redis Stream Job으로 만들고 Worker가 처리하게 합니다.
  • 사용자 화면용 report/easy-report를 구성하고 raw trace를 숨깁니다.

대표 API 흐름

POST /api/v1/cases/:caseId/analyze-text
POST /api/v1/cases/:caseId/analyze-video
GET  /api/v1/cases/:caseId/analysis-progress
GET  /api/v1/cases/:caseId/result
GET  /api/v1/cases/:caseId/report
GET  /api/v1/cases/:caseId/easy-report
POST /api/v1/cases/:caseId/reanalyze

사용자에게는 하나의 서비스처럼 보이지만, 내부적으로는 Gateway가 요청을 정리하고 Agent/Worker/DB를 연결합니다.

9. Worker와 영상 분석

영상은 크고 오래 걸리므로 Gateway와 분리된 Worker에서 비동기로 처리합니다.

영상 분석 단계

  1. Gateway가 업로드 정보를 저장하고 Redis Stream에 Job을 넣습니다.
  2. Worker가 영상을 로컬 작업 경로로 materialize합니다.
  3. ffprobe로 duration, fps, 해상도 등 메타데이터를 읽습니다.
  4. ffmpeg로 사고 전후 대표 프레임을 추출합니다.
  5. YOLO가 차량, 사람, 자전거 등 객체 후보를 탐지합니다.
  6. OpenAI 프레임 분석이 장면 설명과 사고 단서를 보강합니다.
  7. Worker가 관찰값을 sanitize하고, YOLO 근거가 부족한 직접 충돌 후보는 낮춥니다.
  8. 정리된 video_input_contract를 Agent에 전달합니다.
설계 이유: 영상 AI의 관찰값은 “최종 판단”이 아니라 분석에 넣는 증거 후보입니다. 예를 들어 영상에 보행자가 보였더라도 직접 충돌 대상이 아니라 context_only면 대분류를 바꾸지 않게 했습니다.

10. Frontend 동작 방식

프론트는 분석 엔진이 아니라 사용자가 정확한 사실을 입력하도록 돕는 인터페이스입니다.

입력 단계

  • 사고 설명을 자연어로 입력합니다.
  • 영상 업로드를 선택할 수 있습니다.
  • 사고 대분류와 세부 유형 선택을 보조합니다.
  • 선택 답변은 structured_facts로 변환됩니다.

질문 단계

  • Agent가 필요한 추가 질문을 내려줍니다.
  • 차대차, 차대사람, 차대자전거 등 대분류별 질문이 달라집니다.
  • “잘 모르겠어요” 답변은 unknown_adjustments로 이어집니다.

결과 단계

  • 한 줄 결론, 대분류, 과실비율, KNIA 기준, 가감요소를 카드로 보여줍니다.
  • raw JSON, trace, chunk_id 같은 내부 정보는 일반 화면에서 숨깁니다.
  • 고급 진단은 접힌 영역에서만 확인할 수 있게 정리합니다.

11. 기술 선택 비교

발표에서 “왜 이 기술을 썼나요?”라는 질문이 나왔을 때 바로 답할 수 있는 비교표입니다.

영역 현재 선택 대안 선택 이유 트레이드오프
Frontend Vue 3 + Vite React, Next.js 컴포넌트 구조가 단순하고 Vite 빌드가 빠릅니다. SPA 중심 서비스에 적합합니다. SEO 중심 공개 페이지가 핵심이면 Next.js가 더 유리할 수 있습니다.
Gateway Fastify + TypeScript Express, NestJS Fastify는 빠르고 schema 기반 검증이 좋으며, Nest보다 구조가 가볍습니다. 대규모 조직형 DI 구조가 필요하면 NestJS가 더 익숙할 수 있습니다.
Agent API FastAPI Flask, Node.js Python AI/RAG 생태계와 잘 맞고, 타입 힌트 기반 API 구현이 쉽습니다. Node 단일 스택보다 런타임이 하나 더 늘어납니다.
장기 작업 Redis Streams HTTP sync, Celery, RabbitMQ, Kafka 도입이 가볍고 이미 Redis를 캐시에도 활용하므로 운영 부담이 작습니다. 초대규모 이벤트 스트리밍은 Kafka가 더 강합니다.
RAG 저장소 PostgreSQL + pgvector Pinecone, Weaviate, Elasticsearch, Chroma 케이스/Job/결과와 벡터 검색을 같은 DB에서 관리해 운영 복잡도를 낮춥니다. 전문 벡터 DB보다 대규모 벡터 운영 기능은 제한적일 수 있습니다.
영상 분석 ffmpeg + YOLO + OpenAI OpenAI-only, YOLO-only YOLO는 객체 후보를 안정적으로 잡고, OpenAI는 장면 해석을 보강합니다. 두 분석 결과를 병합하는 정책이 필요합니다.
Agent 설계 통제형 파이프라인 + 제한적 LLM 완전 자율 Agent 법률/보험 도메인에서는 재현성, 근거 추적, 대분류 guard가 중요합니다. 자유로운 탐색성은 낮지만 결과 안정성이 높습니다.

12. 왜 PostgreSQL + pgvector인가?

RAG만 생각하면 전문 벡터 DB도 가능하지만, 팀 프로젝트 운영 관점에서는 통합 저장소가 더 현실적입니다.

장점

  • 케이스, 업로드, Job, 결과, KNIA chart, RAG chunk를 한 DB에서 트랜잭션으로 관리합니다.
  • SQL 필터와 벡터 검색을 같이 쓸 수 있어 party_type, scenario_type, chart_no 제한 검색이 쉽습니다.
  • 외부 벡터 DB 비용과 네트워크 의존성을 줄입니다.
  • 마이그레이션으로 schema를 추적할 수 있습니다.

다른 선택지와 비교

  • Pinecone: 운영 편의와 확장성은 좋지만 외부 비용과 벤더 의존성이 큽니다.
  • Weaviate: 검색 기능은 강하지만 별도 운영 컴포넌트가 늘어납니다.
  • Elasticsearch: 키워드 검색은 강하지만 벡터와 트랜잭션 데이터 통합은 복잡해질 수 있습니다.
  • Chroma: 로컬 개발은 빠르지만 제품 DB와 분리되어 운영 일관성이 떨어질 수 있습니다.

13. 왜 구조화 chart 우선인가?

법률·보험 도메인에서 가장 위험한 것은 근거 없는 숫자 생성입니다.

LLM-only RAG의 문제

단순 RAG는 관련 문단을 가져온 뒤 LLM이 답변을 조합합니다. 하지만 과실비율은 숫자이기 때문에, LLM이 문단을 잘못 해석하거나 없는 비율을 만들어내면 사용자에게 큰 오해를 줄 수 있습니다.

단순 RAG

  • 문서 chunk 검색
  • LLM이 근거와 숫자를 함께 생성
  • 빠르게 만들 수 있지만 hallucination 위험

LawCompass 방식

  • 구조화 chart에서 base_fault와 adjustments 추출
  • RAG는 설명과 법규 보강에 사용
  • 숫자 생성은 chart 기반으로 제한
발표 문장: “저희는 RAG를 했지만, RAG 문단에서 LLM이 과실비율을 새로 만들게 하지 않았습니다. 과실 숫자는 구조화 chart에서 가져오고, RAG는 왜 그 기준을 참고하는지 설명하는 데 사용했습니다.”

14. 판단 품질을 지키는 장치

분류 오류, 근거 누수, 확정 표현을 줄이기 위한 안전장치입니다.

Party Router

직접 충돌 대상을 먼저 확정해 대분류를 고정합니다. 환경 단어보다 직접 충돌 대상이 우선입니다.

Party Guard

대분류 밖 KNIA chart와 RAG chunk가 최종 결과에 나오지 않도록 걸러냅니다.

Evidence Quality

근거가 부족하면 judgment를 낮추고 추가 질문이나 참고용 기준으로 표시합니다.

Unknown Handling

모르는 가감요소는 확정 과실에 바로 반영하지 않고 조건별 결과로 분리합니다.

15. 발표 대본 예시

슬라이드 설명처럼 바로 읽을 수 있는 짧은 대본입니다.

전체 구조 소개

“LawCompass는 Frontend, Gateway, Worker, Agent, PostgreSQL, Redis로 구성했습니다. Frontend는 사용자의 입력과 결과 표시를 담당하고, Gateway는 케이스 API와 Job 생성을 담당합니다. 영상처럼 오래 걸리는 작업은 Worker가 비동기로 처리하고, Agent는 사고 분류와 RAG 기반 판단에 집중합니다. PostgreSQL은 일반 데이터와 pgvector 기반 RAG 데이터를 함께 저장하고, Redis는 Job queue와 캐시에 사용합니다.”

RAG 설명

“저희 RAG의 특징은 KNIA 기준을 단순 문서로만 넣지 않았다는 점입니다. chart_no, 대분류, 사고유형, 기본 과실, 가감요소를 구조화해서 저장하고, 설명 문단은 rag_documents로 분리했습니다. 분석할 때는 구조화 chart를 먼저 찾고, 선택된 chart_no 또는 같은 대분류 안에서만 RAG chunk를 검색합니다. 그래서 차대사람 사고에 차대차 기준이 섞이는 문제를 줄였습니다.”

영상 분석 설명

“영상은 Gateway에서 바로 분석하지 않고 Redis Stream Job으로 넘깁니다. Worker는 ffmpeg로 프레임을 추출하고 YOLO와 OpenAI를 함께 사용해 관찰값을 만듭니다. 다만 영상 관찰값은 최종 판단이 아니라 보조 증거입니다. 사용자가 직접 입력한 충돌 대상과 영상 관찰값이 충돌하면 신뢰도와 conflict로 남기고 Agent가 판단합니다.”

기술 선택 설명

“Fastify Gateway와 FastAPI Agent를 분리한 이유는 웹 API 안정성과 AI 분석 생태계를 모두 가져가기 위해서입니다. Redis Streams는 Kafka보다 가볍고 팀 프로젝트 규모에 적합했습니다. pgvector는 전문 벡터 DB보다 확장 기능은 적지만, 케이스 데이터와 RAG 데이터를 한 PostgreSQL 안에서 관리할 수 있어 구현과 운영이 단순해졌습니다.”

16. 예상 질문과 답변

기술 심화 질문에 대비하기 위한 Q&A입니다.

Q1. 왜 RAG를 사용했나요?

교통사고 과실 판단은 일반 상식이 아니라 KNIA 기준, 법률 근거, 사고 유형별 수정요소에 의존합니다. 모델의 일반 지식만 쓰면 근거가 불명확하고 최신 기준과 다를 수 있습니다. 그래서 KNIA 구조화 chart와 법률/해설 문서를 검색해 근거 기반으로 답하도록 RAG를 사용했습니다.

Q2. 왜 벡터 검색만 하지 않고 구조화 chart를 먼저 찾나요?

과실비율은 숫자입니다. 벡터 검색 문단을 LLM이 읽고 숫자를 만들면 hallucination 위험이 있습니다. LawCompass는 chart의 base_fault와 adjustments를 먼저 찾고, RAG는 설명을 보강하는 용도로 사용합니다.

Q3. 차대사람 사고에서 차대차 기준이 나오지 않게 어떻게 막나요?

Party Router가 직접 충돌 대상을 기준으로 대분류를 고정하고, Party Guard가 대분류에 맞지 않는 chart prefix를 제거합니다. 예를 들어 car_vs_person이면 보 계열만 허용하고 차41, 차43 같은 차대차 기준은 rejected mismatch로 내부 기록만 남깁니다.

Q4. pgvector 대신 Pinecone을 쓰지 않은 이유는?

Pinecone은 관리형 벡터 DB로 편하지만 외부 비용과 의존성이 생깁니다. 이 프로젝트는 케이스 데이터, Job, 분석 결과, RAG chunk가 모두 PostgreSQL에 있으므로 pgvector를 쓰면 SQL 필터와 벡터 검색을 한 DB에서 처리할 수 있어 구조가 단순합니다.

Q5. Redis Streams를 선택한 이유는?

영상 분석은 시간이 오래 걸리므로 API 요청에서 동기 처리하면 timeout이 발생할 수 있습니다. Redis Streams는 가볍게 Job queue를 만들 수 있고, 이미 Redis를 cache에 쓰기 때문에 운영 컴포넌트를 늘리지 않아도 됩니다. Kafka는 대규모 이벤트 스트리밍에는 좋지만 팀 프로젝트 규모에서는 과합니다.

Q6. Agent가 MCP인가요?

현재 구현은 표준 MCP 클라이언트/서버라기보다, MCP-like tool registry와 specialist pipeline을 가진 통제형 Agent 구조입니다. 발표에서는 “표준 MCP를 완전히 구현했다”라고 말하기보다 “도구 실행과 근거 라우팅을 분리한 MCP 지향 구조”라고 표현하는 것이 정확합니다.

Q7. 영상 분석 결과가 틀리면 어떻게 하나요?

영상 관찰값은 최종 판단이 아니라 evidence 후보입니다. YOLO와 OpenAI 관찰값이 충돌하거나 직접 충돌 대상 신뢰도가 낮으면 context_only 또는 conflict로 표시하고, 사용자 입력과 추가 질문을 통해 보정합니다.

Q8. review_required chart는 왜 사용하는가?

review_required는 사람이 검수할 필요가 있다는 metadata입니다. 다만 party, scenario, chart_no, base_fault, raw_text가 충분히 맞는 대표 기준이면 참고 근거로 활용할 수 있습니다. base_fault가 비어 있거나 대분류가 불일치하면 final 확정값으로 쓰지 않습니다.

Q9. LLM은 어디에 쓰이나요?

LLM은 자연어 요약, 사고 설명 정리, 법률 근거 설명, 질문 생성, 보고서 문장화에 주로 사용합니다. 과실비율 숫자는 가능한 구조화 chart와 가감요소 계산 결과를 사용하고, LLM이 임의 생성하지 않도록 정책을 둡니다.

Q10. 이 구조의 한계는 무엇인가요?

KNIA JSON의 검수 품질과 coverage에 영향을 받습니다. 영상 분석도 프레임 추출 위치나 화질에 따라 관찰값이 달라질 수 있습니다. 그래서 결과는 법적 확정이 아니라 보험 실무 참고와 추가 확인 항목 제시로 표현합니다.

정확성을 위해 표현을 조심해야 하는 부분입니다.

피해야 할 표현

  • “표준 MCP를 완전히 구현했습니다.”

  • “구조화 chart를 우선 사용하고, 검수 필요 항목은 참고 기준으로 표시합니다.”
  • “RAG와 party guard로 근거 누수와 임의 생성을 줄였습니다.”

18. 발표 마무리 문장

7분 발표의 마지막 20초에 사용하기 좋은 정리입니다.

“정리하면 LawCompass는 단순 챗봇이 아니라, 사고 대분류를 먼저 확정하고, 그 대분류 안에서 KNIA 구조화 기준과 RAG 근거를 검색한 뒤, 영상 관찰값과 추가 질문을 통해 불확실성을 줄이는 서비스입니다. Gateway, Worker, Agent, PostgreSQL/pgvector를 분리해 웹 응답성과 AI 분석 안정성을 모두 확보했고, 과실비율 숫자는 LLM이 임의 생성하지 않도록 구조화 chart 중심으로 제한했습니다. 이 점이 일반적인 LLM 챗봇형 법률 상담과 가장 큰 차이입니다.”

20. End-to-End 동작 예시

면접식 질문에 대비해 특정 입력이 내부에서 어떻게 이동하는지 단계별로 정리했습니다.

공사 담당자 사고

  1. 사용자 입력에 “공사 담당자”, “도로 폭 측정”, “갑자기 튀어나와 사고”가 들어옵니다.
  2. Party Router가 직접 충돌 대상을 사람/도로 작업자로 보고 car_vs_person을 확정합니다.
  3. Scenario Classifier는 교차로나 도로 단어에 끌려가지 않고 보행자/작업자 사고 계열을 선택합니다.
  4. Party Guard는 보 계열 chart만 허용하고 차43, 차41, 거 계열을 제외합니다.
  5. KNIA Matcher는 같은 차대사람 대분류 안에서 가장 가까운 기준을 찾습니다.
  6. 동적 질문은 작업자 위치, 갑작스러운 진입, 안전조치, 시야, 차량 속도, CCTV를 묻습니다.
  7. Report는 “직접 충돌 대상이 사람인 차대사람 사고”라고 설명하고 내부 정책 문구는 숨깁니다.

차선변경 사고

  1. 입력에 “상대 차량”, “깜빡이 없이 차선변경”, “내 차 옆 충돌”이 들어옵니다.
  2. Party Router가 상대 차량과 직접 충돌했으므로 car_vs_car로 고정합니다.
  3. Scenario Classifier가 lane_change_collision을 선택하고 사용자 역할을 직진 차량으로 매핑합니다.
  4. 검색어는 진로변경, 차로변경, 동일방향, 후행 직진차, 진로변경차로 확장됩니다.
  5. KNIA Matcher가 차43 또는 차43-2 후보를 찾고 보행자/자전거 기준은 제외합니다.
  6. Fault Adjuster는 차선변경 주체, 방향지시등, 선진입, 충돌 부위 같은 가감요소를 반영합니다.
  7. 결과는 내 과실이 낮은 방향의 기준을 사용자 관점으로 설명합니다.

21. 추가 예상 질문

발표 후 Q&A에서 나올 수 있는 꼬리질문을 짧게 대비합니다.

Q11. 기존 검색어 기반 분류와 무엇이 다른가요?

검색어만 보면 “도로”, “교차로”, “차량” 같은 환경 단어가 사고유형을 흔들 수 있습니다. 현재 구조는 직접 충돌 대상을 먼저 잡고, 그 다음 검색어와 시나리오를 제한합니다.

Q12. 같은 대분류 fallback은 왜 필요한가요?

정확히 같은 chart가 없더라도 사용자는 참고 기준을 기대합니다. 다만 다른 대분류 기준은 오해를 만들기 때문에 같은 대분류 안에서만 reference_only fallback을 제공합니다.

Q13. 법률 RAG와 KNIA RAG는 왜 나눴나요?

KNIA는 과실비율 실무 기준이고 법률 RAG는 도로교통법 등 법적 근거입니다. 숫자 산정과 법률 설명의 역할이 다르므로 evidence family를 나눠 관리합니다.

Q14. evidence_family_counts는 왜 중요한가요?

분석 결과가 법률 설명만 있고 KNIA 근거가 없으면 과실비율 판단 품질이 떨어질 수 있습니다. 그래서 회귀 테스트에서 필요한 시나리오는 KNIA family evidence가 포함되는지 확인합니다.

Q15. 후미추돌에서 브레이크등을 모르면 어떻게 처리하나요?

브레이크등 고장은 앞차 과실을 올릴 수 있는 요소지만, 모름이면 확정 반영하지 않습니다. unknown_adjustments와 conditional_outcomes로 보내 “확인되면 달라질 수 있음”으로 표시합니다.

Q16. Gateway가 Agent를 직접 호출하면 결합도가 높지 않나요?

텍스트 분석은 비교적 짧은 요청이므로 Gateway가 Agent 내부 API를 호출합니다. 영상처럼 긴 작업은 Worker와 Redis Stream으로 분리해 결합도와 timeout 위험을 낮췄습니다.

Q17. 왜 모든 작업을 Worker로 보내지 않았나요?

짧은 텍스트 분석까지 비동기로 보내면 사용자 경험과 상태 관리가 불필요하게 복잡해집니다. 오래 걸리는 영상 분석만 비동기로 분리했습니다.

Q18. OpenAI API 장애가 나면 어떻게 되나요?

KNIA structured chart, keyword fallback, static fallback을 둬 최소한의 기준 탐색이 가능하도록 설계했습니다. 다만 자연어 설명 품질과 영상 장면 해석은 제한될 수 있습니다.

Q19. RAG chunk가 잘못 매칭되면요?

chart_no와 major_party_type으로 먼저 제한하고, evidence routing에서 사고 축과 맞지 않는 근거는 primary에서 제외합니다. 사용자 화면에는 불일치 근거를 표시하지 않습니다.

Q20. 이 서비스가 법률 자문인가요?

아닙니다. 보험 실무 기준과 법률 근거를 바탕으로 참고 가능한 분석을 제공하는 도구입니다. 최종 판단은 보험사 협의, 분쟁심의, 경찰 조사, 법원 판단에 따라 달라질 수 있습니다.
