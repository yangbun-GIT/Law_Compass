7분 발표 대본

운영 방식: 1~11번은 사용자 흐름을 빠르게 보여주고, 12~19번에서 문제·해결·아키텍처·Agent 판단 구조를 설명합니다. 20~26번은 데모와 근거 화면, 27~29번은 한계와 마무리입니다. 슬라이드 6~8처럼 같은 주제가 반복되는 곳은 빠르게 넘기면 7분 안에 들어옵니다.

1

LawCompass 소개

교통사고 영상 기반 과실비율 분석 AI 서비스
12초

안녕하세요. 저희 팀은 교통사고 직후 사용자가 가진 영상과 사고 설명을 바탕으로, KNIA 과실비율 기준과 법령 근거를 함께 정리해 주는 LawCompass를 개발했습니다. 핵심은 AI가 판결을 내리는 것이 아니라, 판단에 필요한 사실과 근거, 추가 확인 항목을 구조화해서 보여주는 것입니다.

전달 의도
서비스의 정체성을 “판단 보조”로 못 박고 시작합니다.
2

사용자 흐름 먼저보기

입력부터 결과까지 한 화면 흐름
12초

먼저 사용 흐름입니다. 사용자는 메인 페이지에서 케이스를 만들고, 영상이나 자연어 설명을 입력합니다. 이후 일반 사용자 모드와 전문가 모드를 선택하고, 과실비율에 영향을 주는 보완 질문에 답하면 결과 카드로 이어집니다.

전달 의도
기술 설명 전에 제품 흐름을 먼저 이해시킵니다.
3

메인 페이지

케이스 생성·최근 분석·KNIA 검색 순위
8초

메인 페이지는 사용자가 바로 사고 케이스를 만들 수 있도록 구성했습니다. 최근 분석 결과와 KNIA 검색 순위도 함께 배치해서, 이전 결과 확인과 새 분석 진입이 한 화면에서 가능하도록 했습니다.

전달 의도
사용자가 헤매지 않고 바로 입력으로 들어간다는 점을 강조합니다.
4

사고 상황 입력과 영상 업로드

영상·자연어·구조화 답변
12초

입력은 세 단계로 받습니다. 영상은 사고 장면의 핵심 근거가 되고, 자연어 설명은 사용자가 기억하는 상황을 보완합니다. 다만 자연어는 오해가 있을 수 있기 때문에, 선택형 구조화 답변을 더 높은 신뢰도로 반영하도록 설계했습니다.

전달 의도
입력별 신뢰도 차이를 설명해 AI 오판 우려를 줄입니다.
5

출력 모드 선택

일반 사용자 모드와 전문가 모드
10초

결과는 사용자 수준에 따라 나눴습니다. 일반 사용자에게는 현재 상황, 예상 과실, 핵심 근거를 쉽게 보여주고, 전문가 모드에서는 기준번호, 가감요소, 법령·판례, trace처럼 검토에 필요한 정보를 더 자세히 보여줍니다.

전달 의도
같은 분석 결과를 다른 정보량으로 보여주는 전략을 설명합니다.
6

일반 사용자 모드

쉬운 결과 화면
6초

일반 사용자 모드는 복잡한 내부 로그를 줄이고, 지금 사고가 어떤 유형인지와 어떤 사실이 더 확인되어야 하는지를 중심으로 읽히게 했습니다.

전달 의도
일반 화면에서 내부 trace를 숨긴 이유를 짧게 말합니다.
7

전문가 모드

기준번호·가감요소·법령/판례
6초

전문가 모드는 보험 대응이나 분쟁 검토에 필요한 근거를 더 자세히 확인하는 화면입니다. 기준번호와 수정요소, 관련 법규를 함께 볼 수 있습니다.

전달 의도
전문가 모드가 단순 디버그가 아니라 검토용 화면임을 설명합니다.
8

전문가 모드 상세

근거 프레임과 trace 확인
6초

특히 영상 기반 분석에서는 어떤 프레임을 근거로 관찰했는지가 중요합니다. 그래서 전문가 모드에서는 근거가 되는 프레임과 판단 trace를 확인할 수 있게 했습니다.

전달 의도
영상 분석의 설명 가능성을 짚습니다.
9

과실비율에 영향을 주는 질문

사고유형별 동적 질문
14초

과실비율은 사고유형과 세부 사실에 따라 크게 바뀝니다. 예를 들어 후미추돌은 정차 사유와 브레이크등, 차선변경은 방향지시등과 충돌 부위가 중요합니다. 그래서 LawCompass는 사고유형별로 필요한 질문만 우선순위로 묻습니다.

전달 의도
질문 기능이 단순 폼이 아니라 과실 산정에 연결된다는 점을 말합니다.
10

분석 진행과 비동기 처리

Redis Stream 기반 영상 job
16초

영상 분석은 파일 크기와 길이에 따라 시간이 오래 걸립니다. 그래서 업로드 API는 빠르게 응답하고, 실제 영상 전처리와 프레임 분석은 Redis Streams 기반 Worker job으로 분리했습니다. 실패해도 전체 서비스가 멈추지 않고 해당 job만 재시도할 수 있습니다.

전달 의도
MSA 분리의 이유를 사용자 경험과 장애 격리로 연결합니다.
11

실제 결과 페이지

조건부 결과·예상 과실·근거 연결
20초

결과 화면은 먼저 현재 상황을 정리하고, 그 다음 조건부 결과와 예상 과실비율을 보여줍니다. 단일 숫자만 크게 보여주면 사용자가 확정 판정으로 오해할 수 있기 때문에, 어떤 근거가 있고 어떤 사실이 확인되면 달라지는지를 함께 표시했습니다.

전달 의도
“숫자보다 근거와 조건”이라는 제품 철학을 설명합니다.
12

프로젝트 목표

사고 직후 기준 해석의 어려움
18초

문제는 사고 직후 사용자가 영상은 갖고 있어도, 이 상황이 어떤 KNIA 기준에 가까운지, 어떤 법령이나 사실이 중요한지 판단하기 어렵다는 점입니다. 일반 LLM은 그럴듯한 답을 만들 수 있기 때문에, 저희는 판결이 아니라 근거 수준과 추가 확인 질문을 제공하는 방향으로 목표를 잡았습니다.

전달 의도
일반 LLM 환각과 LawCompass의 차이를 분명히 합니다.
13

Solution

영상·진술·공식기준을 판단 계약으로 연결
20초

해결 방식은 LLM이 바로 결론을 내지 않게 하는 것입니다. 먼저 입력을 사실 계약으로 구조화하고, 확정된 사실과 불확실한 사실, 서로 충돌하는 사실을 분리합니다. 그 다음 KNIA 기준과 법령 RAG를 검색하고, 기본 과실과 가감요소를 조건부로 조정합니다.

전달 의도
판단 파이프라인의 핵심 단계를 요약합니다.
14

전체 MSA 아키텍처

웹 요청·영상 장기 분석·AI 판단 분리
24초

전체 구조는 Frontend, Gateway, Worker, Agent, PostgreSQL, Redis로 나뉩니다. Frontend는 Gateway만 호출하고, Gateway가 인증·업로드·DB 저장·결과 조립을 담당합니다. 영상 장기 분석은 Redis Streams와 Worker가 처리하고, Agent는 입력 정규화, 사고유형 판단, KNIA·법령 근거 검색, 과실비율 조정을 담당합니다. 여기서 KNIA/Legal은 별도 서비스라기보다 DB와 pgvector에 적재된 지식 소스입니다.

전달 의도
현재 프로젝트 구조와 맞게 KB를 “별도 MSA”가 아닌 “지식 데이터”로 설명합니다.
15

기술 스택

Vue·Fastify·FastAPI·Redis·PostgreSQL
16초

프론트는 Vue 3와 Vite, Gateway는 Fastify와 TypeScript, Agent와 Worker는 Python 기반으로 구성했습니다. PostgreSQL과 pgvector는 케이스 데이터와 근거 검색을 함께 담고, Redis는 영상 job과 진행 상태 캐시에 사용합니다. Docker Compose로 전체 서비스를 묶었습니다.

전달 의도
각 기술의 역할을 짧게 연결합니다.
16

Runtime Flow

Gateway와 Worker 실행 흐름
20초

실행 흐름은 케이스 생성, 영상 저장, Redis job 생성, Worker의 프레임 추출, Agent의 사실 중재와 근거 검색, 마지막 easy-report 생성 순서입니다. Gateway는 사용자 요청과 결과 조립을 맡고, Worker는 ffprobe와 ffmpeg로 영상 전처리, 대표 프레임 추출, OpenAI와 YOLO 기반 관찰 후보 생성을 맡습니다.

전달 의도
업로드와 분석이 분리되어 있다는 점을 운영 흐름으로 설명합니다.
17

Agent 판단 흐름

LLM 한 번 호출이 아닌 단계별 검증
26초

Agent는 입력 정규화, 영상 관찰 계약, fact arbitration, scenario classifier, KNIA retriever, legal retriever, fault composer, report composer로 나뉩니다. 중요한 점은 보이는 객체와 실제 충돌 대상을 분리한다는 것입니다. 예를 들어 오토바이가 화면에 보인다고 해서 오토바이와 직접 충돌한 사고로 확정하지 않고, 직접 접촉 여부를 별도 fact로 검증합니다.

전달 의도
프로젝트의 핵심 안전장치인 fact 분리와 party guard를 설명합니다.
18

영상 관찰값 계약과 오염 방지

객체 관찰과 법적 사실 분리
18초

영상 관찰값은 confidence와 frame reference가 있어야 fact로 승격됩니다. 또 영상 관찰값, 구조화 답변, 자연어 설명은 서로 다른 신뢰도로 처리합니다. 확실하지 않은 경우에는 과실비율에 바로 반영하지 않고 추가 질문으로 전환합니다.

전달 의도
영상 AI 결과를 무조건 믿지 않는 구조를 강조합니다.
19

RAG와 근거 연결

KNIA·법령·판례·도로구조 근거군
18초

근거는 하나로 섞지 않고 근거군을 나눴습니다. KNIA는 기준번호와 기본 과실, 가감요소를 담당하고, 법령 RAG는 도로교통법 같은 법적 맥락을 보조합니다. 판례와 도로구조 자료는 직접 적용보다 참고 근거로 구분하고, 사고축과 맞지 않으면 primary가 아니라 reference로 낮춥니다.

전달 의도
RAG 결과를 등급화하고 사고축 불일치를 막는 방식을 설명합니다.
20

실제 영상 기반 예시 3개

서로 다른 판단축
16초

데모는 서로 다른 판단축을 보여주도록 구성했습니다. 어린이보호구역 오토바이·자전거 사례, 좁은길 교차로 전동킥보드 사례, 비좁은 커브길 비접촉 오토바이 단독 전도 사례입니다. 각 사례는 단순 분류보다 어떤 fact가 과실 방향을 바꾸는지에 집중했습니다.

전달 의도
데모가 다양한 edge case를 보여준다는 점을 설명합니다.
21

Demo Case 1

어린이보호구역 오토바이·자전거
14초

첫 번째 사례는 어린이보호구역과 제한속도, 자전거와 어린이 여부가 함께 등장합니다. 여기서는 보호구역을 가감요소 후보로 두고, 자전거인지 보행자인지, 어린이인지 아닌지를 분리해 조건부 결과로 보여줍니다.

전달 의도
대상 분류와 보호구역 가감요소를 분리합니다.
22

Demo Case 2

좁은길 교차로 전동킥보드
14초

두 번째 사례는 좁은길 교차로에서 전동킥보드가 등장합니다. 신호 질문만 던지는 것이 아니라, 진입 전 정지 여부, 반사경 확인, 상대 접근 가능성, 우측 서행과 시야 확보 의무를 먼저 확인하도록 질문을 정교화했습니다.

전달 의도
질문 우선순위가 사고 맥락에 따라 달라진다는 점을 설명합니다.
23

Demo Case 3

비접촉 오토바이 단독 전도
18초

세 번째 사례는 직접 접촉이 없는 오토바이 단독 전도입니다. 이 경우 오토바이가 화면에 보이더라도 차대이륜차 직접 충돌 기준으로 보내면 안 됩니다. 그래서 direct_contact_with_ego=false와 opponent_single_fall=true를 별도 fact로 관리하고, 접촉사고 기준은 primary가 아닌 참고 기준으로 낮춥니다.

전달 의도
오분류 방지의 대표 사례로 설명합니다.
24

KNIA 검색 순위와 후보 기준

사고군별 후보에서 상세 기준으로
12초

KNIA 화면에서는 먼저 검색 순위와 대분류를 보고, 그 다음 기준번호와 사고유형을 확인합니다. 현재 구조에서는 대분류 party guard를 적용해서 차대사람 사고에 차대차 기준이 섞이지 않도록 관리합니다.

전달 의도
KNIA 검색이 단순 키워드 검색이 아니라 대분류 guard를 거친다는 점을 말합니다.
25

상세 기준과 가감요소

기본 과실과 수정요소 분리
14초

1. 제품 가치와 문제 정의

Q1 LawCompass가 해결하려는 가장 핵심 문제는 무엇인가요?

사고 직후 사용자가 영상은 갖고 있어도 어떤 과실 기준과 법령 근거를 봐야 하는지 모른다는 문제입니다. LawCompass는 영상을 근거 후보로 만들고, KNIA 기준과 법령 RAG를 연결해 참고 범위와 추가 확인 항목을 제시합니다.

Q2 일반 LLM에게 사고 상황을 물어보는 것과 무엇이 다른가요?

일반 LLM은 그럴듯한 과실비율을 만들어낼 위험이 있습니다. 저희는 먼저 사실을 구조화하고, KNIA·법령 근거와 사고 대분류 guard를 통과한 결과만 사용자에게 보여주는 방식으로 환각 위험을 줄였습니다.

Q3 이 서비스가 법률 자문인가요?

아닙니다. LawCompass는 확정 판결이나 법률 자문을 대신하지 않고, 사고 접수와 보험사 대응 전에 필요한 사실·근거·질문을 정리하는 보조 도구입니다.

Q4 사용자가 가장 먼저 얻게 되는 가치는 무엇인가요?

“내 사고가 어떤 유형인지”, “어떤 기준을 봐야 하는지”, “무엇을 더 확인해야 하는지”를 빠르게 알 수 있습니다. 숫자 하나보다 왜 그 범위가 나왔는지를 설명하는 데 초점을 둡니다.

Q5 타깃 사용자는 누구인가요?

1차 타깃은 사고 직후 보험사와 대화해야 하는 일반 운전자입니다. 확장하면 손해사정, 보험 실무자, 법률 상담 전 사전 정리 도구로도 사용할 수 있습니다.

Q6 왜 과실비율을 단일 숫자로 확정하지 않나요?

과실비율은 신호, 속도, 충돌 부위, 정차 사유 같은 사실에 따라 달라집니다. 확인되지 않은 사실이 있으면 단일 숫자가 오해를 만들 수 있어서 범위와 조건부 결과를 함께 보여줍니다.

Q7 프로젝트의 차별점은 무엇인가요?

영상 관찰값, 사용자 진술, 구조화 질문, KNIA 기준, 법령 RAG를 하나의 판단 계약으로 묶었다는 점입니다. 특히 직접 충돌 대상과 사고 대분류가 섞이지 않도록 party guard를 둔 것이 핵심입니다.

Q8 사용자가 영상을 올리지 않아도 사용할 수 있나요?

가능합니다. 자연어 설명과 구조화 질문만으로도 사고유형과 필요한 근거를 찾을 수 있습니다. 다만 영상이 없으면 일부 사실은 확인 필요로 남습니다.

Q9 사용자가 설명을 잘못 입력하면 어떻게 하나요?

자연어 입력은 낮은 신뢰도 fact로 두고, 구조화 답변과 영상 관찰값으로 보완합니다. 서로 충돌하면 바로 확정하지 않고 conflicting 또는 uncertain 상태로 남겨 추가 질문을 유도합니다.

Q10 왜 “질문” 기능이 중요한가요?

과실비율은 누락된 세부 사실 때문에 크게 바뀝니다. 질문 기능은 사고유형별로 중요한 fact를 채워서 근거 검색과 가감요소 적용의 정확도를 높입니다.

2. 사용자 경험과 화면 구성

Q11 일반 사용자 모드와 전문가 모드를 왜 나눴나요?

일반 사용자는 빠른 이해와 다음 행동이 중요하고, 전문가는 기준번호와 가감요소, 법령·판례, trace가 중요합니다. 같은 분석 결과라도 필요한 정보량이 달라서 화면을 분리했습니다.

Q12 일반 사용자 화면에서 내부 trace를 숨긴 이유는 무엇인가요?

trace_id, source_type, metadata 같은 정보는 일반 사용자에게 혼란을 줍니다. 대신 “추가 확인 필요”, “참고용 기준”, “같은 대분류의 가까운 기준”처럼 사람이 이해할 수 있는 표현으로 바꿨습니다.

Q13 결과 페이지의 읽는 순서는 어떻게 설계했나요?

먼저 한 줄 결론과 사고 대분류를 보여주고, 그 다음 예상 과실, KNIA 기준, 가감요소, 불확실 항목, 지금 해야 할 일을 보여주는 흐름입니다. 사용자가 결론에서 근거로 자연스럽게 내려가도록 구성했습니다.

Q14 질문 화면은 어떻게 사용자 친화적으로 만들었나요?

전문 용어보다 쉬운 질문 문장을 사용하고, “잘 모르겠어요” 선택지를 제공합니다. 또한 질문마다 왜 중요한지를 한 줄로 설명해 사용자가 답변 이유를 이해하도록 했습니다.

Q15 최근 UI 개선의 핵심은 무엇인가요?

개발자용 로그처럼 보이던 화면을 줄이고, 고대비 다크 테마와 카드형 구조로 정리했습니다. 사용자 화면에서는 raw key나 내부 정책 문구가 보이지 않도록 정제했습니다.

Q16 모바일에서도 사용할 수 있나요?

프론트엔드는 Vue 3 기반 반응형 UI로 구성되어 있어 모바일 사용을 고려했습니다. 긴 결과는 카드와 접힘 구조로 나누어 읽기 부담을 줄이는 방향입니다.

Q17 결과가 너무 복잡해지지 않나요?

그래서 일반 모드에서는 핵심 결론, 예상 범위, 추가 확인 항목 중심으로 보여주고, 상세 근거는 접힌 카드나 전문가 모드로 이동시킵니다.

Q18 보험사에 말할 문장 기능은 왜 필요한가요?

사용자는 결과를 받아도 실제로 어떻게 말해야 할지 어려워합니다. 확인된 사실과 근거를 바탕으로 보험사에 전달할 문장을 제공하면 후속 행동으로 연결됩니다.

Q19 챗봇은 어떤 역할인가요?

분석 결과를 다시 질문하거나, 사고 접수에 필요한 내용을 정리하는 후속 인터페이스입니다. 단독 판단 엔진이라기보다 결과 해석과 보완 답변 흐름을 돕습니다.

Q20 왜 KNIA 기준을 사용자가 직접 검색할 수 있게 했나요?

사용자가 분석 결과 외에도 유사 기준을 직접 확인할 수 있어야 신뢰가 생깁니다. 다만 최종 결과에는 사고 대분류와 맞는 기준만 보여주도록 제한합니다.

3. 전체 아키텍처와 서비스 경계

Q21 현재 구조는 진짜 MSA인가요?

단일 저장소 모노레포 안에서 Frontend, Gateway, Agent, Worker, DB, Redis를 Docker Compose 기반으로 분리한 경량 MSA 구조입니다. 배포 단위와 책임 경계를 분리했다는 의미에서 MSA 성격을 갖습니다.

Q22 Frontend가 Agent를 직접 호출하지 않는 이유는 무엇인가요?

인증, 권한, 업로드, DB 저장, 사용자용 payload 정리를 Gateway에서 통제하기 위해서입니다. Frontend는 Gateway만 호출하고 내부 서비스는 Gateway와 Worker가 연결합니다.

Q23 Gateway의 핵심 책임은 무엇인가요?

인증, 공개 API 라우팅, 업로드 처리, DB 저장, Redis job enqueue, Agent 내부 호출, 결과 리포트 조립입니다. 사용자 화면에 보여줄 payload와 관리자 진단 payload를 분리하는 역할도 합니다.

Q24 Worker는 왜 따로 뺐나요?

영상 분석은 오래 걸리고 실패 가능성이 높습니다. Worker를 분리하면 업로드 API는 빠르게 응답하고, 장기 작업은 Redis Streams job으로 재시도와 상태 관리를 할 수 있습니다.

Q25 Agent는 어떤 역할을 담당하나요?

Agent는 입력 정규화, 직접 충돌 대상 판단, 사고유형 분류, KNIA·법령 근거 검색, 과실비율 조정, 판단 상태와 리포트 생성의 중심입니다.

Q26 PostgreSQL과 pgvector는 어떻게 쓰이나요?

PostgreSQL은 케이스, job, 분석 결과, KNIA 구조화 chart, 법령 RAG chunk를 저장합니다. pgvector는 근거 검색에서 벡터 기반 유사도 검색을 지원합니다.

Q27 Redis는 어떤 역할인가요?

Redis Streams는 영상 분석 job queue로 쓰이고, Redis는 진행 상태나 일부 캐시에도 사용됩니다. 장기 작업과 즉시 API 응답을 분리하는 데 핵심입니다.

Q28 KNIA/Legal은 별도 서비스인가요?

현재 구현에서는 별도 MSA 서비스가 아니라 DB와 pgvector에 적재된 지식 데이터와 RAG 소스입니다. 발표에서는 “Imported Knowledge” 또는 “지식 소스”로 설명하는 것이 정확합니다.

Q29 왜 Docker Compose를 사용했나요?

팀 프로젝트 환경에서 Frontend, Gateway, Agent, Worker, DB, Redis, Caddy를 일관되게 띄우기 위해서입니다. 운영 복잡도를 줄이면서 서비스 경계를 확인할 수 있습니다.

Q30 Caddy는 어떤 역할인가요?

Caddy는 reverse proxy와 운영 진입점 역할을 합니다. 외부 요청을 프론트와 API Gateway로 정리해 전달하는 구조에 맞춰 사용합니다.

4. 영상 처리와 Worker

Q31 영상 분석은 어떤 순서로 진행되나요?

업로드된 영상은 Worker가 ffprobe로 메타데이터를 확인하고, ffmpeg로 대표 프레임을 추출합니다. 이후 YOLO와 OpenAI vision을 통해 객체와 장면 관찰 후보를 만들고 Agent에 전달합니다.

Q32 YOLO가 사고를 판단하나요?

아닙니다. YOLO는 차량, 보행자, 자전거, 오토바이 같은 객체 후보를 찾는 보조 관찰 모델입니다. 사고 판단과 과실비율 판단은 Agent가 입력 facts와 근거를 종합해 수행합니다.

Q33 OpenAI vision은 어떤 역할인가요?

대표 프레임에서 장면 맥락과 관찰 후보를 얻는 데 사용합니다. 다만 이것도 확정 사실이 아니라 confidence와 frame reference가 붙은 관찰값으로 다룹니다.

Q34 영상만으로 과실비율을 확정할 수 있나요?

대부분 어렵습니다. 영상에 보이지 않는 신호, 속도, 정차 사유, 브레이크등 작동 여부 같은 정보가 필요할 수 있으므로 질문과 조건부 결과가 함께 제공됩니다.

Q35 영상 분석이 실패하면 전체 분석도 실패하나요?

그렇게 설계하지 않았습니다. 영상 job이 실패하면 해당 관찰값은 failure observation이나 확인 필요 상태로 남기고, 자연어와 구조화 답변 기반 분석은 가능한 범위에서 진행할 수 있습니다.

Q36 대표 프레임은 어떻게 고르나요?

Worker가 영상 길이와 이벤트 후보 구간을 기준으로 대표 프레임을 추출합니다. 현재는 ffmpeg/ffprobe 기반 전처리와 필요 시 dense fallback을 사용합니다.

Q37 야간이나 블러 영상은 어떻게 처리하나요?

confidence가 낮거나 관찰 근거가 부족하면 확정 fact로 승격하지 않습니다. 사용자에게 시야, 조도, CCTV, 목격자 같은 추가 확인 질문으로 전환합니다.

Q38 보이는 객체가 사고 대상이 아닐 수도 있는데 어떻게 막나요?

Agent는 context object와 direct collision partner를 분리합니다. 예를 들어 횡단보도가 보인다고 보행자 사고로 바꾸지 않고, 직접 충돌 대상이 무엇인지 별도 fact로 확인합니다.

Q39 비접촉 사고는 어떻게 처리하나요?

direct_contact_with_ego=false, opponent_single_fall=true 같은 fact를 별도로 관리합니다. 직접 접촉이 없으면 차대이륜차 접촉 기준을 primary로 쓰지 않고 참고 기준으로 낮춥니다.

Q40 영상 원본은 어디에 저장되나요?

현재 동작 경로는 로컬 storage/uploads 기반입니다. S3 provider는 계획 또는 미구현 provider 성격이며, 실제 secret이나 원본 대용량 영상은 Git에 포함하지 않습니다.

5. Agent, 사고유형, 직접 충돌 대상

Q41 Agent가 가장 먼저 판단하는 것은 무엇인가요?

직접 충돌 대상과 KNIA 대분류입니다. 사람, 차량, 자전거, 오토바이, 시설물, 단독 사고를 먼저 나누어 다른 대분류 기준이 섞이지 않게 합니다.

Q42 party guard란 무엇인가요?

사고 대분류에 맞는 KNIA chart만 최종 결과에 남기기 위한 필터입니다. 예를 들어 차대사람 사고에서는 보행자 계열 기준만 허용하고, 차대차 기준은 사용자 화면에 표시하지 않습니다.

Q43 “공사 담당자가 튀어나왔다”는 어떤 사고로 분류하나요?

직접 충돌 대상이 공사 담당자, 도로 작업자, 사람이라면 car_vs_person으로 분류합니다. 도로, 공사, 차량 같은 환경 단어보다 직접 충돌 대상이 우선입니다.

Q44 자전거를 탄 사람은 보행자인가요?

직접 충돌 대상이 자전거를 탄 사람이라면 차대자전거로 봅니다. 그냥 사람이나 작업자, 보행자와 충돌한 경우에는 차대사람으로 봅니다.

Q45 오토바이와 충돌하면 어떤 대분류인가요?

직접 충돌 대상이 오토바이나 이륜차라면 car_vs_motorcycle로 분류합니다. 단, 화면에 오토바이가 보이는 것과 직접 충돌은 구분합니다.

Q46 시설물과 충돌한 경우는 어떻게 하나요?

라바콘, 방호벽, 가드레일, 전봇대 같은 기물과 직접 충돌했다면 car_vs_object 또는 프로젝트 정책상 단독 사고로 처리합니다. 보행자 기준은 사용하지 않습니다.

Q47 차대차 사고에서 보행자 키워드가 나오면 어떻게 하나요?

보행자가 단순 배경 정보라면 차대사람으로 승격하지 않습니다. 직접 충돌 대상이 차량이면 car_vs_car를 유지하고 보행자 기준은 제외합니다.

Q48 scenario_classifier는 어떤 역할인가요?

대분류를 새로 흔드는 역할이 아니라, 확정된 대분류 안에서 후미추돌, 차선변경, 교차로, 보행자 사고 같은 세부 scenario를 정하는 역할입니다.

Q49 12대 중과실은 대분류인가요?

아닙니다. 12대 중과실은 대분류가 아니라 risk tag 또는 가중 요소 후보입니다. 음주운전이나 신호위반이 있다고 민사 과실을 자동으로 100:0 확정하지 않습니다.

Q50 사용자 입력과 영상 관찰값이 충돌하면 무엇을 우선하나요?

고신뢰 영상 관찰값과 구조화 답변을 우선하되, 무조건 덮어쓰지는 않습니다. 충돌 상태를 남기고 추가 확인이 필요한 항목으로 표시합니다.

6. KNIA, RAG, 근거 품질

Q51 KNIA 기준은 어디에서 가져오나요?

2023.6 자동차사고 과실비율 인정기준 JSON의 structured charts와 rag_documents를 사용합니다. charts는 과실 기준 후보, rag_documents는 해설과 참고 근거로 사용합니다.

Q52 RAG는 어떤 역할인가요?

RAG는 기준의 설명, 관련 법규, 활용 참고사항을 찾아주는 역할입니다. 과실 숫자의 source of truth는 가능한 구조화 chart의 base_fault와 adjustment 후보가 됩니다.

Q53 review_required chart는 어떻게 처리하나요?

사람 검수가 필요한 metadata로 표시하되, party와 scenario가 맞고 base_fault와 원문 근거가 충분하면 근거 품질을 무조건 낮추지는 않습니다. base_fault가 비어 있거나 역할 매핑이 불명확하면 reference_only로 낮춥니다.

Q54 KNIA 기준이 없으면 어떻게 하나요?

다른 대분류 기준으로 넘어가지 않고, 같은 대분류 안에서 가장 가까운 참고 기준을 fallback으로 보여줍니다. 그래도 부족하면 no_knia_match_reason과 추가 확인 항목을 남깁니다.

Q55 차대사람 사고에서 차대차 기준이 나오지 않도록 어떻게 막나요?

party_guard가 chart prefix와 major_party_type을 검사합니다. car_vs_person이면 보 계열 chart만 허용하고, 차43이나 차41 같은 차대차 chart는 rejected mismatch로 내부 기록만 남깁니다.

Q56 RAG 검색도 대분류 제한이 되나요?

네. chart_no가 선택되면 해당 chart_no의 rag_documents를 우선 검색하고, chart_no가 없으면 같은 major_party_type 안에서만 검색하도록 제한합니다.

Q57 차선변경 사고는 어떤 KNIA 기준을 사용하나요?

car_vs_car의 lane_change_collision에서는 차43 계열, 특히 역할과 상황이 맞는 subchart 후보를 우선 매핑합니다. 사용자가 직진 차량인지 진로변경 차량인지에 따라 사용자 관점 과실을 반대로 매핑합니다.

Q58 후미추돌 사고는 어떤 기준을 사용하나요?

대표적으로 차41 기준을 사용합니다. 앞차 피해자 역할이면 뒤차 100, 앞차 0 방향을 기본으로 보고, 급정거 사유나 브레이크등 고장 여부는 가감요소로 처리합니다.

Q59 법령 RAG와 KNIA RAG의 차이는 무엇인가요?

KNIA RAG는 보험 실무상 과실비율 기준과 가까운 근거이고, 법령 RAG는 도로교통법 등 법적 의무의 맥락을 설명합니다. 최종 과실비율 산정에서는 KNIA 기준이 더 직접적인 기준입니다.

Q60 판례는 어떻게 사용하나요?

판례는 직접 적용보다는 유사 쟁점과 판단 경향을 참고하는 근거입니다. 사고축과 맞지 않으면 primary evidence가 아니라 참고 근거로 낮춥니다.

7. 과실비율과 가감요소

Q61 과실비율은 LLM이 직접 만들나요?

그렇게 설계하지 않았습니다. 구조화 KNIA chart의 base_fault와 adjustment 후보를 우선 사용하고, LLM은 근거 설명이나 보조 요약에 제한적으로 사용합니다.

Q62 가감요소는 어떻게 적용하나요?

확정된 사실에 해당하는 항목만 applied_adjustments로 반영합니다. 모르는 항목은 숫자를 바꾸지 않고 unknown_adjustments와 conditional_outcomes에 넣습니다.

Q63 브레이크등 작동 여부를 모르면 어떻게 하나요?

후미추돌에서 브레이크등 고장이 확인되면 앞차 과실이 늘 수 있지만, 모른다면 확정 과실에 바로 반영하지 않습니다. 대신 확인되면 달라질 수 있는 조건부 결과로 표시합니다.

Q64 차선변경 사고에서 중요한 질문은 무엇인가요?

누가 차선변경했는지, 방향지시등 사용 여부, 충돌 부위, 선진입, 속도 차이, 실선/점선 여부가 중요합니다. 이 fact들이 사용자 과실 방향과 범위를 바꿉니다.

Q65 교차로 사고에서 중요한 질문은 무엇인가요?

신호 상태, 상대 신호 확인 가능성, 진입 순서, 진행 방향, CCTV나 신호주기표 여부입니다. 상대의 적색 신호 진입이 확인되면 과실 방향이 크게 달라질 수 있습니다.

Q66 보행자 사고에서 중요한 질문은 무엇인가요?

횡단보도 여부, 보행자 위치, 갑작스러운 진입 여부, 운전자 시야, 차량 속도, 도로공사 안전조치, CCTV나 목격자 여부가 중요합니다.

Q67 음주운전이면 무조건 100:0인가요?

아닙니다. 음주운전은 중요한 위험요소와 가중 요소가 될 수 있지만, 민사 과실비율을 자동으로 100:0으로 확정하지 않습니다. 사고 발생과 손해 확대의 인과관계를 함께 봐야 합니다.

Q68 과실 합계는 어떻게 관리하나요?

final_fault는 항상 내 과실과 상대 과실의 합이 100이 되도록 보정합니다. 값은 0~100 범위를 넘지 않도록 제한합니다.

Q69 조건부 결과는 왜 필요한가요?

아직 확인되지 않은 사실이 결과를 바꿀 수 있기 때문입니다. 예를 들어 급정거 사유가 정당한지, 브레이크등이 고장인지에 따라 같은 후미추돌도 결과가 달라질 수 있습니다.

Q70 보험사 대응 문장은 어떻게 만들어지나요?

확인된 사실, KNIA 기준, 불확실 항목을 바탕으로 사용자가 말할 수 있는 문장으로 정리합니다. 다만 확정적 법률 주장이 아니라 근거 확인 요청에 가깝게 표현합니다.

8. 데이터, 보안, 개인정보

Q71 영상 개인정보는 어떻게 다루나요?

영상 원본에는 차량번호와 얼굴이 포함될 수 있으므로 저장·표시 정책이 중요합니다. 현재 발표에서는 개인정보 보호가 운영 리스크이며, 원본 영상과 대용량 산출물은 Git에 포함하지 않는다고 설명하면 됩니다.

Q72 .env나 API 키는 어디에 저장하나요?

실제 secret은 코드나 문서에 넣지 않습니다. `.env` 값, API key, JWT secret, NAS 계정 등은 Git에 커밋하지 않는 것이 원칙입니다.

Q73 사용자의 사고 영상은 외부로 전송되나요?

현재 구조에서는 로컬 저장소에 업로드하고, 필요 시 대표 프레임 관찰을 위해 OpenAI vision 같은 외부 API를 사용할 수 있습니다. 이 경우 운영 단계에서는 사용자 동의와 개인정보 처리 정책이 필요합니다.

Q74 DB에는 어떤 정보가 저장되나요?

케이스, 업로드 metadata, job 상태, 분석 결과, KNIA chart, RAG chunk, 일부 trace metadata가 저장됩니다. 사용자 화면에는 내부 trace나 raw metadata를 그대로 노출하지 않습니다.

Q75 분석 결과의 신뢰도를 어떻게 표시하나요?

evidence coverage, judgment status, finality display 같은 상태를 통해 근거 기반 참고, 조건부 결과, 추가 확인 필요를 구분합니다. 일반 화면에는 사람이 이해할 수 있는 문구로 변환합니다.

Q76 법령 최신성은 어떻게 관리하나요?

법령과 판례는 ingestion 날짜와 출처 관리가 필요합니다. 현재는 RAG 소스와 구조화 기준을 연결하는 구조를 만들었고, 운영 단계에서는 갱신 주기와 검수 프로세스가 필요합니다.

Q77 KNIA JSON은 자동 추출 결과인가요?

2023.6 기준 PDF에서 생성한 검수용 JSON을 사용합니다. review_required가 true인 항목은 최종 확정 기준처럼 단정하지 않고 낮은 confidence 또는 참고 기준으로 표시합니다.

Q78 데이터베이스 migration이 자주 필요한 구조인가요?

필요할 때만 idempotent migration을 추가하는 원칙입니다. 대부분의 trace와 진단 정보는 기존 JSON metadata에 additive로 보존해 DB schema 변경을 최소화했습니다.

Q79 raw prompt나 provider 오류가 노출되나요?

일반 사용자 화면에는 노출하지 않습니다. 관리자 진단에서도 raw prompt, API key, token, provider raw stack 대신 안전한 요약 message와 error_type 중심으로 표시합니다.

Q80 비용 관리는 어떻게 고려했나요?

OpenAI frame analysis와 YOLO 관찰에 대해 사용량 metadata와 fallback reason을 남기도록 설계했습니다. 운영 단계에서는 모델 호출량, 프레임 수, retry, 저장소 비용을 추적해야 합니다.

9. 테스트, 회귀, 운영 안정성

Q81 어떤 테스트를 중점적으로 했나요?

Agent regression, KNIA matcher, party guard, structured chart import, fault adjuster, Gateway report composer, Frontend display/chat test를 중점적으로 검증했습니다.

Q82 회귀 테스트에서 가장 중요한 케이스는 무엇인가요?

후미추돌 피해자, 상대 차선변경, 사용자 차선변경, 교차로 신호위반, 자전거 충돌, 영상과 사용자 입력 충돌 케이스가 중요합니다. 이 케이스들이 사고축과 근거 품질을 검증합니다.

Q83 car_vs_person에 차대차 기준이 섞이지 않는지 어떻게 검증했나요?

party guard 테스트와 no cross-party leak 테스트로 검증합니다. 직접 충돌 대상이 사람이면 보 계열 기준만 최종 결과에 남아야 합니다.

Q84 영상 분석 테스트는 실제 API 없이도 가능한가요?

가능합니다. fixture와 reference metrics를 사용해 OpenAI/YOLO 없이도 계약 수준을 검증할 수 있습니다. 실제 영상 E2E는 API와 모델이 켜진 환경에서 별도로 확인합니다.

Q85 CI에서 Agent Contracts가 실패했던 원인은 무엇이었나요?

structured KNIA chart가 review_required라는 이유로 evidence coverage가 불필요하게 낮아지는 문제가 있었습니다. party와 scenario가 맞고 base_fault와 원문 근거가 있으면 회귀 테스트에서 근거 품질을 유지하도록 조정했습니다.

Q86 failure observation은 무엇인가요?

OpenAI/YOLO나 tool 호출이 실패했을 때 조용히 성공처럼 보이지 않게 남기는 안전한 관찰값입니다. 원시 오류 대신 safe_message와 fallback_reason을 기록합니다.

Q87 trace_id는 왜 중요한가요?

Gateway 요청, Worker job, Agent analysis, DB 저장 결과를 하나의 흐름으로 추적하기 위해 필요합니다. 장애나 품질 문제를 재현할 때 핵심입니다.

Q88 Docker 환경이 없는 경우에도 검증할 수 있나요?

일부 Frontend/Gateway/문서 검증은 로컬에서 가능합니다. 다만 Agent는 Python 의존성 차이가 있을 수 있어 Docker 컨테이너 기준 검증을 우선합니다.

Q89 운영에서 가장 취약한 지점은 무엇인가요?

영상 품질, 외부 Vision API 비용과 실패, 근거 데이터 최신성, 개인정보 처리, KNIA coverage가 취약 지점입니다. 그래서 fallback과 reference_only, 추가 질문 흐름이 필요합니다.

Q90 테스트가 특정 샘플에만 맞춰지는 위험은 어떻게 줄였나요?

여러 사고축 reference fixture와 contamination 테스트를 사용해 보행자 배경, 신호 불확실성, 중앙선 장애물, 작은 대상 recall 같은 다양한 케이스를 확인했습니다.

10. 한계, 확장, 발표 방어 질문

Q91 표준 MCP를 구현한 건가요?

표준 MCP Host/Client/Server를 완전히 도입한 것은 아닙니다. 현재는 Agent 내부 MCP-like tool registry/executor를 구현했고, 향후 표준 MCP로 확장할 수 있도록 pilot과 gate를 문서화했습니다.

Q92 왜 표준 MCP를 바로 도입하지 않았나요?

현재 문제는 외부 tool server 연동보다 Agent 내부 판단 계약과 근거 품질 안정화가 더 중요했습니다. cross-host 재사용이나 표준 MCP client 요구가 명확해지면 도입을 재검토하는 구조입니다.

Q93 실제 법원 판단과 다르면 어떻게 하나요?

LawCompass 결과는 확정 판결이 아니라 참고 범위입니다. 실제 판단은 경찰 조사, 보험사 협의, 분쟁심의, 법원 판단에 따라 달라질 수 있음을 명확히 표시합니다.

Q94 KNIA에 없는 사고는 분석할 수 없나요?

분석 자체는 가능하지만 과실비율은 확정적으로 제시하지 않습니다. 같은 대분류의 가까운 참고 기준과 법령 근거, 추가 확인 질문을 제공하는 방식으로 처리합니다.

Q95 앞으로 가장 먼저 개선할 기능은 무엇인가요?

KNIA·법령 데이터 coverage 확대, 실제 영상 E2E 품질 평가, 개인정보 비식별화, 사용량·비용 모니터링, 보완 질문 UX 개선이 우선 과제입니다.

Q96 모바일 앱으로 확장할 계획이 있나요?

현재는 웹 MVP가 중심입니다. 추후에는 모바일 업로드 경험과 온디바이스 전처리를 검토할 수 있지만, 지금은 서버 기반 분석 안정화가 우선입니다.

Q97 실시간 사고 분석도 가능한가요?

현재 구조는 업로드 후 비동기 분석에 맞춰져 있습니다. 실시간 분석은 프레임 스트리밍, 비용, 지연 시간, 개인정보 이슈가 커서 별도 설계가 필요합니다.

Q98 팀 프로젝트 범위에서 가장 큰 기술적 성과는 무엇인가요?

단순 LLM 호출이 아니라 입력 fact, 영상 관찰값, KNIA 구조화 기준, 법령 RAG, 과실 가감요소, 사용자 표시 finality를 하나의 파이프라인으로 연결한 점입니다.

Q99 평가위원이 “그냥 챗GPT 프롬프트 아닌가요?”라고 물으면?

프롬프트만이 아니라 Frontend, Gateway, Worker, Agent, PostgreSQL/pgvector, Redis Streams가 분리된 실행 구조입니다. Agent 내부에서도 facts, party guard, KNIA matcher, fault adjuster, report composer를 거쳐 결과를 만듭니다.

Q100 한 문장으로 프로젝트를 요약하면?

LawCompass는 교통사고 영상과 진술을 근거 기반 fact로 정리하고, KNIA·법령 기준과 연결해 과실비율 참고 범위와 추가 확인 질문을 제공하는 AI 사고 분석 보조 서비스입니다.
